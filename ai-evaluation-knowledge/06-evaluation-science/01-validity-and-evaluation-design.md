# 有效性与评测设计

## 1. 从决策开始，而不是从榜单开始

先写一句可验证的目标，例如：“在中文售后问题上，系统能否在不违反退款政策的前提下，把订单状态改成用户请求的状态？”这比“评测 agent 智能”更容易确定样本、成功条件和失败代价。

把测量链分成五层：

**目标现象 → 可观察任务 → 输入/运行条件 → 评分 → 关于真实使用的结论。**

每一层都需要论证。选择题可以测知识，但不能直接证明系统能完成真实工作；程序通过测试可以说明满足被测行为，但不能直接证明代码安全、可维护或不会破坏未覆盖功能。Bean 等对 445 篇 benchmark 论文的系统审查将“现象、任务、指标、结论”拆开审视，并给出明确构念、代表性抽样、污染防范、统计比较和错误分析建议。这是一项对特定会议与年份论文的审查，不是对所有 benchmark 的普查。[论文 §1–3](https://arxiv.org/html/2511.04703v1)

## 2. 四种常混淆的质量

| 性质 | 要问的问题 | 不能替代什么 |
|---|---|---|
| 正确实施 | 输入、答案、日志、评分和分母是否按协议执行？ | 实施正确不证明任务代表真实需求 |
| 可靠性 | 换 seed、重跑、换标注者，结果是否稳定？ | 稳定不证明准确 |
| 构念有效性 | 分数是否主要反映声称要测的能力？ | 一个高相关总分不能排除格式或长度混杂 |
| 外部适用性 | 对目标语言、领域、人群、工具和部署条件是否仍成立？ | 学术题效果不自动迁移到线上工作 |

这是实务拆解，不是声称四类穷尽测量理论。Weidinger 等强调评测应覆盖模型之外的系统与使用情境，并形成部署前评测和部署后观察的反馈循环。[论文 §3](https://arxiv.org/html/2503.05336v3)

## 3. 明确被测对象

建议把结果对象写为：

`model version + system prompt + agent scaffold + tools + decoding + budget + task release + grader version`。

“同一模型”若一方允许搜索、执行代码、尝试十次或用更大 token 预算，另一方不允许，比较的是两个系统条件。它可以是公平且有用的产品比较，但应明确比较对象，不能归因于权重本身。

HELM 原始设计将场景与指标拆开，在标准化条件下同时考察准确率、校准、鲁棒性、公平性、偏差、毒性和效率。这里引用其设计原则，不把旧实验的模型排名当当前结论。[原始论文摘要](https://arxiv.org/abs/2211.09110)

## 4. 如何建立一个可用的任务集

### 4.1 先写抽样框

定义任务来自哪些用户流程、语言、领域、时间窗口和难度层。保留真实分布样本，同时可设置单独的困难集与高风险集。

困难集回答“能否处理边界情况”，流量加权集回答“总体体验如何”。不能把困难集平均分说成线上总体成功率，也不能让大量简单请求掩盖高风险失败。

### 4.2 每个任务应有一份最小评测契约

- 输入与初始环境。
- 允许操作、工具和资源预算。
- 完成条件，以及不允许出现的副作用。
- 参考答案或可接受行为集合。
- 可观测证据、评分方法、超时与错误处理。
- task ID、版本、来源时间、独立抽样单位。

对于 agent，目标状态通常比某一条固定操作轨迹更有意义，但涉及政策约束时还需要过程检查。仅看最终状态可能漏掉越权操作；强行匹配参考轨迹又可能排除正确替代路径。

### 4.3 评分前验证任务

先验证一个正确解能过；再构造几个“看起来像对、实则有错”的解，确认会失败。检查多种正确实现是否都被接受。这分别针对错误拒绝和错误接受，不能只检查一边。

### 4.4 分析混杂因素

- 格式：是不是答对但 JSON/标签格式没对？如果格式本来就是目标，则应算错；否则应单独报告。
- 长度：偏好更长是否等于内容更好？
- 语言：英文解析器是否适用于中文？
- 工具：失败来自模型规划、工具错误还是环境故障？
- 预算：更高分来自推理改善还是更多尝试？

## 5. 做负面对照比再加一个总分更有价值

建议至少设置：明确错误答案、正确答案的不同表述、包含否定词的答案、无关但流畅的长答案、格式偏差、空输出、工具超时、测试未启动、以及可能诱导评分器的内容。

这些是诊断集，不应冒充随机代表性样本。诊断失败能够证明某个机制存在，无法单凭几个例子估计它在生产中的频率。本目录 [D4 评分实验](experiments/README.md) 正按这个边界解释。

## 6. 不要把质量审计误读成“模型已经解决了剩余问题”

2026 年 SWE-bench 两次审计表明，即使经过人工筛选，任务说明与测试仍可能错位。但“测试有问题”既可能低估能力，也可能高估能力：过严测试拒绝正确解，低覆盖测试放过错误解。不能简单把所有被标记的问题加回分数。[Verified 审计](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)、[Pro 审计](https://openai.com/index/separating-signal-from-noise-coding-evaluations/)

## 7. 一个评测结论应该长什么样

较好的表述：在固定版本的 1,000 个独立售后任务上，同一预算条件下，系统 A 的成功率比 B 高 2 个百分点，配对差值区间为某范围；高风险退款子集未见明确改善；执行失败另列；结果不涵盖语音或真实支付。

较差的表述：A 比 B 智能 2%，所以可以直接上线。
