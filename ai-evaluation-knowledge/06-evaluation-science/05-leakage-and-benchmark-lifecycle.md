# 污染、泄漏与 benchmark 生命周期

## 1. 把“污染”拆开说

以下是本研究的操作分类，不声称文献统一采用这些名称：

| 风险 | 具体例子 | 为什么影响结论 |
|---|---|---|
| 直接题目泄漏 | 训练语料含测试题与答案 | 很难区分记忆与未见题泛化 |
| 解答或补丁泄漏 | 训练含 gold patch、解析或测试断言 | 可能获得提示中未提供的信息 |
| 来源材料预暴露 | 看过用来出题的文章、考试或仓库历史 | 新提问不代表底层信息未见 |
| 模板/近重复 | 改人名、换数字或改写后仍保留解题模板 | “未逐字重复”不等于任务新颖 |
| 开发泄漏 | 反复看测试分数选择提示词和系统配置 | 测试集变成了开发集 |
| 运行时泄漏 | agent 搜索到公开答案，读取隐藏文件或评测日志 | 测量的是包含这些信息的系统条件 |
| 评分器泄漏/操纵 | 候选文本诱导 judge，或补丁伪造测试日志 | 分数不再表示任务完成 |

不能把所有相关训练都叫作弊。训练数学知识后解未见数学题是预期能力；关键是预先定义需要测哪一级泛化，以及哪些信息在部署时本来可用。

## 2. 污染证据的强弱不同

### 较直接的证据

- 在可审计训练语料中找到测试数据或解答。
- 模型在有限线索下复现难以偶然命中的题目细节、独特补丁或原始错误。
- 在明确假设下通过校准过的污染检验。

### 只能作为线索的证据

- 旧题分高、新题分低。
- 改写后明显退步。
- 模型说自己见过该题。
- 题目似然较高，或成员推断分数偏高。

这些也可能由分布变化、题目难度、tokenization 或提示变化造成。应设计匹配对照，不能一条线索直接证明全部训练过程。

## 3. “黑盒证明污染”方法的适用条件

Oren 等利用数据集的可交换性：若模型与数据独立，规范顺序不应系统性地比随机重排更可能。方法比较原始顺序与重排后的 log likelihood；有限 Monte Carlo permutation test 需要加一校正，p 值最小为 `1/(m+1)`。分片版本用跨 shard 的似然差进行检验。[论文 §2–3](https://arxiv.org/html/2310.17623v2#S2)

必须保留的限制：

- 需要序列 log probability 访问，并非只有聊天文本的任意黑盒 API 都可直接用。
- 有限样本 permutation 保证和分片 t-test 的渐近保证不是同一个东西。
- 真实数据排序可能不满足可交换性，需了解生成过程与负面对照。
- 对逐字数据顺序记忆敏感，不保证发现改写、来源材料或其它部分污染。
- 未检出不等于没有污染；检测功效会受重复频次、规模和查询预算影响。

原文也说明其展示 p 值未做多重检验校正；正式部署检测时应明确检验族与校正方案。[论文 §6](https://arxiv.org/html/2310.17623v2#S6)

## 4. LiveBench：动态与客观评分仍有边界

LiveBench 将近期信息来源、定期更新和自动评分结合，旨在减少静态题集与 LLM judge 的问题。其 2025 年论文描述每次更新后重跑模型、更改评分器后重评输出，并保留版本。[附录 A.4–A.6](https://arxiv.org/html/2406.19314v2#A1.SS4)

但同一论文附录 A.7 明确承认其部分题目源自更早的编程与数学内容，因此并非完全满足“所有测试题均未被训练见过”。不要把项目名或“contamination-limited”改写为“保证零污染”。

动态更新也带来新的测量问题：如果题目不断变难，今天 60% 和六个月前 60% 不是同一个尺度。比较趋势需要固定版本、共同锚题或明确的等值设计。刷新频率、私有题比例及最新实施状态还应单独核验；这里引用的是论文协议，不冒充当前逐月履约记录。

## 5. SWE-bench 的两次官方质量审计

### 2026-02-23：Verified

OpenAI 审计了 138 道 o3 在 64 次重复运行中未能稳定解决的题，占 500 题的 27.6%。报告称被审计子集的 59.4% 有测试/任务描述问题，并展示了模型复现某些题目细节或 gold patch 的证据。[官方报告](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)

**关键限定：138 题按模型失败筛选，不能把 59.4% 当成整套 500 题的随机抽样缺陷率。** 复现案例也不能给出全部模型、全部题目的污染比例。报告是重要的一手审计，但仍是模型提供商的研究，独立复查有价值。

### 2026-07-08：Pro

后续报告对 731 道公开任务先筛出 286 道可能有问题的任务，再分别进行 agent 辅助复核和五位工程师的人工评审。两条路径分别认定 200 和 249 道有破坏性问题，对应全公开集的 27.4% 与 34.1%。作者据此估计约 30%，并**明确撤回此前推荐 Pro 的建议**。[较新官方报告](https://openai.com/index/separating-signal-from-noise-coding-evaluations/)

这些比例是该筛选与复核流程识别出的范围，不是从随机样本估计、附有置信区间的普遍缺陷率。未被第一阶段筛出的任务是否也有缺陷，报告流程无法完全排除。

其中一个案例是任务说明要求一个空格，隐藏测试要求两个空格。这样的失败不应简单解释为缺乏代码能力；反之，低覆盖测试也可能错误地奖励不完整修复。

## 6. 一个 benchmark 应如何被维护

### 任务版本

保留任务内容、来源、答案、生成器版本、修订原因。修改含义或环境后通常需要重跑；只改可应用于已有输出的评分器时，可重评旧输出，但必须使用新评分版本重评所有比较对象。

### 结果版本

每个结果必须绑定模型快照、调用时间、环境、任务版本、评分版本。供应商浮动别名会增加复现难度，应记录可获得的版本信息及限制。

### 变更与退役

当 benchmark 接近饱和、可公开记忆、任务无法稳定运行、答案错误或不再对应目标使用，应降低其证据权重或退役。保留历史值便于研究，但不要因为“大家一直用”而继续把它当领先指标。

HumanEval 官方仓库在 2026-10-16 标注弃用且不再维护。本目录仍研究它的 pass@k 代码，原因是指标具有教学价值，不是认为其仍适合衡量当前 frontier 能力。[固定提交](https://github.com/openai/human-eval/commit/b9453e8f1865df0a0057a1383767caa400acfbcf)

## 7. 实务防线

- 先确定公开集、开发集、私有最终集的不同用途。
- 训练与评测数据去重既看原文，也看解答、代码、来源材料和近重复。
- 用 canary 与访问记录辅助追踪，但不要把 canary 未命中当成未污染证明。
- 将评测容器、隐藏测试、答案和部署 agent 的可访问环境隔开。
- 对评分器使用负面对照、替代表述和日志完整性检查。
- 对真实工作建立持续的小型新题流，保留旧版本锚点。
- 对外报告污染检查的方法、覆盖范围和不能判断的部分。
