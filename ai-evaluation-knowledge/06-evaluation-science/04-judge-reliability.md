# LLM-as-a-judge：验证判分系统，而不只是挑一个强模型

## 1. 一个 judge 至少有六个组成部分

`模型版本 + rubric + 上下文/参考答案 + 展示顺序 + 输出协议 + 解析/汇总器`。

只记录 judge 模型名，别人无法重现评测。即使自然语言判决正确，输出解析仍可能记成错误结果。[FastChat 固定源码](https://github.com/lm-sys/FastChat/blob/587d5cfa1609a43d192cedb8441cac3c17db105d/fastchat/llm_judge/common.py)

## 2. 不要互换这些概念

| 指标 | 测量的东西 | 典型误读 |
|---|---|---|
| 与参考标签的正确率 | 相对某套标签判对多少 | 标签必然客观且完整 |
| 人与模型 agreement | 两类判决多常一致 | 模型已具有人类所有判断能力 |
| 重复一致率 | 相同输入重跑是否一致 | 稳定就准确 |
| 顺序一致率 | A/B 互换后是否仍选同一答案 | 不偏位置就没有其它偏差 |
| 排名相关 | 模型总体排序是否类似 | 每一题都判得正确 |
| 分组错误率 | 对某类任务/输出的系统性误差 | 高总分自动覆盖弱子集 |

本地构造：参考标签 95 个正例、5 个负例，一个永远判正的 judge 有 95% 准确率和 100% 原样重复一致率，但负例召回为 0，balanced accuracy=50%，Cohen's κ=0。κ 也受标签分布影响，不能取代混淆矩阵和领域解释。[本地结果](experiments/results/statistical_diagnostics.json)

## 3. MT-Bench 的经典证据应该怎样读

原论文针对当时的模型、80 个两轮问题和特定人类标注协议，展示了位置、冗长和数学判分问题。交换答案顺序、引入独立参考答案能够改善其中部分问题。[论文 §3](https://arxiv.org/html/2306.05685v4#S3)

经常被引用的约 85% 人机 agreement 来自**去除 tie 的 S2 口径**。包含 tie/不一致的 S1 口径，GPT-4 pairwise 与人类约 66%。它们不是矛盾结果，而是分母和标签集合不同。原文还发现模型差距较大时更容易达成人机一致。[论文 Table 5、§4](https://arxiv.org/html/2306.05685v4#S4)

因此不能把“80%+ agreement”当成对所有任务、所有新模型、所有语言或所有高风险判断的固定准确率。原论文对 self-enhancement 的结论本身也较谨慎，不能把观察趋势写成已完成因果确认。

## 4. 主观偏好与客观违反指令需要不同的验证集

LLMBar 专门构造一好一坏的答案对，让错误答案可能更流畅、更吸引人，以测试是否真的遵守指令，而不是只学会偏好某种文风。它包含 419 对样本，区分自然集和对抗集。论文分别报告互换顺序后的准确率与一致率。[论文 §2–4](https://arxiv.org/html/2310.07641v2)

这是一个有价值的压力测试，但不能被解释为真实用户请求的随机样本。其对抗集曾针对 ChatGPT 过滤，因此对特定模型可能更难；80 个样本的人类一致性检查也不等于对所有 419 项完成独立多人复标。[作者 README](https://github.com/princeton-nlp/LLMBar)、[论文 §4.2](https://arxiv.org/html/2310.07641v2#S4.SS2)

实务建议：验证集同时包含真实任务的分层随机样本，以及否定、数字、约束、遗漏、漂亮但无关的回答等挑战集。两部分单独报告。

## 5. 长度控制有用，但不是去掉所有偏差

AlpacaEval-LC 用回归模型解释偏好中的长度效应，然后估计双方等长条件下的偏好。在该论文实验中，这减少了通过“多说/少说”改变分数的空间，并把与 Arena 排名的 Spearman 相关从 0.94 提至 0.98。[方法与结果](https://arxiv.org/html/2404.04475v2#S3)

需要同时保留三个限制：

- 这是特定英文指令集、judge 和提示词下的结果。
- “等长比较”是一个明确建模目标，不是所有产品都应追求的价值判断。
- 排名相关提升不等于每题更准确，更不意味着事实、文化或 self-bias 已被解决。原论文报告相关差异的 bootstrap p 值约 0.07，不能把效果写成毫无不确定性的普遍规律。[论文 §4.2、§5](https://arxiv.org/html/2404.04475v2#S4.SS2)

## 6. 一个可执行的 judge 验收流程

1. 明确 rubric：把事实正确、遵守约束、完整性、表达质量拆开；定义致命错误是否一票否决。
2. 建立校准集：专家独立标注、记录争议与理由，先盲评再裁决。
3. 留出验证集：不能在同一批题上反复改 rubric，再用它证明有效。
4. 控制位置：随机化 A/B；对关键样本双向评估，并保留不一致率。
5. 校验参考：reference 不自动正确。尽量用可验证事实、工具结果或独立专家解。
6. 测 parser：唯一 verdict、合法枚举、分数范围、空值、冲突标签、截断输出。
7. 看分层误差：语言、长度、模型家族、任务类型、难度、正确/错误类别。
8. 监测变更：judge、rubric、解析器改变后，重新验证并给结果打版本。

## 7. 交换位置不是免费消除偏差

FastChat pairwise 会做两轮互换，并把 A/B 映射回真实模型 ID；展示逻辑将不一致视为 tie。但这会增加 tie 率，也可能降低发现细小真实差异的能力。它是一种保守汇总策略，不是发现所有偏差的证明。

本地运行同一固定源码时，人工 stub 输出包含“先考虑 [[A]]，最终 [[B]]”，parser 却返回 A，因为代码先检查是否包含 A 标签。单答 `[[11]]` 也被解析成 11，评分函数本身未限制 1–10 范围。这里证明的是解析边界，不是现实模型多常输出这种文本。[D3/D4 记录](case-studies/scorer-execution-traces.md)

## 8. 什么时候不应让 judge 单独决定

高风险部署门槛、事实可程序验证的任务、涉及隐含政策或领域专业判断，以及 judge 自身在校准集上经常失败的区域，应优先采用可验证规则、领域专家与审计机制。多 judge 投票也不保证独立：相似训练和相似提示词可能产生相关错误。

推荐输出是“判决 + 可核查理由/证据 + 未通过的具体 rubric 项 + 不确定/需复核标记”，而不是只有一个漂亮的总分。
