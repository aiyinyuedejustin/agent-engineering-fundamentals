# 从实际问题选择评估组合

适用日期：2026-11-06。以下是对本目录已读证据的有界综合，不是新增 leaderboard，也不是把异构分数相加的建议。目录整体深度以 `benchmark-catalog.json` 及增量记录为准；“适合纳入”不表示本次已经完整跑过。

## 1. 先写一句可被测试的产品声明

与“哪个模型最好”相比，下面这种问题更有用：

> 在给定工具、预算与审批规则下，系统能否完成某类工作，并在失败时留下能定位原因的记录？

然后拆成三个层次：

1. **能力前提**：是否读懂输入、检索证据、生成正确函数或定位 GUI 目标？
2. **系统表现**：把这些能力接起来后，是否实际改变了正确状态、交付了可用文件或完成了流程？
3. **部署结果**：真实用户是否确认完成，成本、延迟、风险与人工纠正是否可接受？

这三层通常需要不同测量。单个榜单不能代替整个验收合同。

## 2. 十种问题，对应十种组合

| 你想知道什么 | 可以从哪些对象开始 | 必须补的对照或条件 |
|---|---|---|
| 知识型回答是否可靠 | MMLU-Pro / GPQA 检查题目推理，SimpleQA 检查短事实回答 | 是否允许检索、答案位置、拒答/不知道、解析错误与真实答错分开 |
| 能否完成研究检索 | BrowseComp 查找难定位的事实；DeepResearchBench 系列查报告与引用 | 短答案成功不能代表完整研究报告；保存搜索权限、网页时间、引用核验与 judge 版本 |
| 能否修复真实代码库 | SWE-bench 指定版本/子集，再加自己仓库的代表性任务 | 仓库状态、测试补丁、容器、工具和预算；防止旧报告被缓存复用。不要仅凭曾经的推荐采用 Pro |
| 能否在终端交付可验收成果 | Terminal-Bench 指定版本与任务类型 | 给产物定义验收脚本，记录 CPU/GPU/时间/网络；任务内 verifier 与运行平台分别审查 |
| 长上下文是否真正有用 | RULER 类受控检索，对照 LongBench v2 长文推理及真实跨轮任务 | 输入长度单位、实际截断、CoT 两阶段、检索块选择、历史压缩及失败分母 |
| 图像、视频或语音输入能否被正确处理 | MMMU / Video-MME 系列 / MMAU 与 VoiceBench 各自分工 | 原媒体与模型实际输入分开登记；帧数/时间点、缩放、字幕、转写和 judge 都可能改变问题 |
| 能否可靠操作 GUI | ScreenSpot-Pro 检查目标定位，OSWorld / AndroidWorld 检查交互结果 | 单帧点击正确不等于完成任务；保存设备、应用、网站、初始状态和状态验收规则 |
| 能否完成服务流程并抵御不可信内容 | τ-bench 系列的业务结果，加 AgentDojo 的效用/攻击目标对照 | 用户模拟器、政策版本、工具权限、状态变化和异常分支；不要把所有 security=True 读作同一种事件 |
| 能否辅助科学与专业工作 | SciCode / PaperBench / MLE-bench / GDPval 等，按交付物类型选择 | 科学函数、论文复现、训练竞赛和职业文件不是同一目标；区分测试覆盖、执行结果与人类偏好 |
| 哪个系统在真实用户中更有用 | Arena 的指定偏好/事实性变体；Agent Arena 的指定部署信号 | 平台人群、缺失反馈、参照池、时间窗、区间和费用；不能把相对效果当绝对成功概率 |

这些是起点，不是每一行都必须全部运行。最小组合通常是一个能够隔离关键能力的评估，加一个与目标工作相近的完整任务评估，再加少量自有场景回放。

## 3. 同名 benchmark，什么时候不能横向比较

出现以下任一变化，应先把两个结果视为不同实验，而不是直接相减：

- 任务池、时间窗、语言、模态或难度子集改变。
- raw media 改为抽帧、转写或文本表示。
- 提供专家背景、金标准前置代码或检索结果。
- 工具集合、agent harness、会话状态或压缩方式改变。
- 思考预算、候选数、重试数或环境动作预算改变。
- parser、judge、测试目标、容差或评分权重改变。
- 缺失/超时/基础设施错误的计入方式改变。
- 缓存和选择规则不同，例如平均多次运行与选择最好一次。

改动并非都不好，重点是它是否回答了同一个问题。Provider Adapter 可以更贴近某供应商产品实际用法，Standard harness 可以更容易控制公共接口；两者都可以有价值，但不应隐去区别。

## 4. 不靠堆 benchmark 数量获得可信度

建议按下面顺序增加投入：

1. **L0 认知**：说清楚被评对象、任务与指标，知道它不测什么。
2. **L1 理解**：读一条真实任务和验收条件，画出数据→提示→输出→判分路径。
3. **L2 实践**：先跑无模型的 smoke test、已知正确/错误样例与分母检查，再运行少量代表性任务。
4. **L3 工程**：冻结版本、环境和数据哈希，隔离不可信代码，记录预算/费用/异常，检查覆盖率和可恢复性，再扩展批量运行。

L0–L3 是学习和使用能力；D0–D4 是证据深度。读过很多论文不等于运行过，完成一个局部函数实验也不等于复现了整套 benchmark。

## 5. 本轮案例如何支持这些判断

- [IFEval](../03-benchmark-cases/ifeval-verifiable-instructions.md)：自然语言要求与已注册可验证约束不一定等宽。
- [Video-MME-v2](../03-benchmark-cases/video-mme-v2-grouped-scoring.md)：相同逐题正确率可能对应不同组分数。
- [ARC-AGI-3](../03-benchmark-cases/arc-agi-3-scoring-and-context.md)：视觉环境、文本 observation 与环境动作效率是三个不同概念。
- [SciCode](../03-benchmark-cases/scicode-scientific-tests-and-bookkeeping.md)：科学测试、串行依赖、给定步骤和分母必须一起检查。
- [AgentDojo](../03-benchmark-cases/agentdojo-utility-and-attack-outcomes.md)：一个布尔字段只有连同事件和分支定义才有意义。
- [Arena](arena-preference-and-agent-signals.md)：偏好、人类确认、反馈子样本和因果相对效果不能互相替代。

可复用的最小记录：模型 snapshot、任务与数据 revision、实际输入表示、提示/状态策略、工具与环境、预算、parser/grader、分母、失败分类、聚合规则、原始产物和成本。缺失哪项，就明确保留哪项不确定性。
