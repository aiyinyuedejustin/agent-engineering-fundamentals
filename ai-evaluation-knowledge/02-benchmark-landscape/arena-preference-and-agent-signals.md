# Arena 不是一种分数：偏好、事实性与部署效果

研究日期：2026-11-06。深度 **D1**：已读官方方法与最新信号定义；未读取生产评分实现、原始用户轨迹或随机分配日志，未复算排行榜。本文不把官方方法声明当成已独立审计的生产事实。

## 1. 先辨认评估对象

| 对象 | 被比较的东西 | 结果如何产生 | 不能直接解释成 |
|---|---|---|---|
| Text Arena 的人类偏好 | 同一用户问题下的两个回答 | 匿名成对选择，再拟合 Bradley–Terry 相对评分 | 客观正确率、任务完成率 |
| Style-control 变体 | 控制部分表现形式后的相对偏好 | 回归中加入长度与 Markdown 特征 | 消除了全部风格或全部混杂 |
| Factuality 变体 | 人类偏好与可核实事实的组合 | 人类投票与事实性软标签共同进入损失 | 所有回答要求的统一正确性 |
| Agent Arena | 平台内执行任务的 orchestrator 选择 | 随机分配后的结果信号与因果效果估计 | 传统 Arena 分数或独立部署的绝对成功率 |

官方 FAQ 说明了匿名投票与 Bradley–Terry；style-control 文章同时明确其分析仍是观察性的，可能存在未观测混杂。事实性文章于 2026-07-14 发布、07-31 更新，介绍 Text/Search 的非默认开关：抽取可用网页核实的原子断言，校准搜索核查的概率，形成软胜负；默认事实性损失权重为 25%。这里的“默认”属于该变体的设置，不表示所有 Arena 榜单已经统一替换为事实性榜单。

来源：[FAQ](https://arena.ai/faq/) · [Style control](https://arena.ai/blog/style-control) · [Factuality 方法](https://arena.ai/blog/factuality-in-arena)

## 2. Agent Arena 必须采用新版信号定义

方法文章首发 2026-06-04，页面更新至 10-15，并明确导向新的定义页。**信号定义页更新于 2026-10-12，应优先于旧文章正文中的早期描述。**

| 当前信号 | 计量事件与分母要点 |
|---|---|
| Confirmed Success | 专门任务完成弹窗中的 yes；所有任务为基础。赞美、普通接受或沉默都不等于确认成功。 |
| Praise vs Complaint | 每任务的赞美数与抱怨数比较；相等，包括没有反馈，不进入有分数任务的成功率。 |
| Steerability | 全部 assistant turns 的平均纠正负担；重复纠正惩罚更高，没有可判断下一轮不认定为重复。 |
| Bash Reliability | 非豁免 bash 调用中的模型归因失败率；正常测试发现问题不算调用失败，外部故障豁免。旧名是 Bash Recovery。 |
| Tool Hallucinations | 工具使用轮次中的虚构工具/能力/签名比例；官方提示基准发生率较低。 |

来源：[2026-10-12 信号定义](https://arena.ai/resources/agent-arena-signals)

这带来一个实际的数据字典要求：不能用同一个字段 `success` 概括所有信号。至少应记录事件单位、原始取值、缺失/豁免规则、聚合分母和定义日期。否则“没点赞”“没有抱怨”“没有工具调用”会被误当成同一种零值。

例如，一个最终没有回复的会话，可以不增加 Confirmed Success，同时不进入 Praise vs Complaint 的有分数任务集合。这是两个不同问题，不是两个评委对同一事件产生了矛盾标签。

## 3. Net Improvement 的参照对象

官方形式化方法将配置从分配分布 P 采样，目标参照分布记为 Q，通常取均匀分布；采用自归一化逆概率权重估计“该组件选择的条件均值减去基线总体均值”，另外使用时间衰减权重，并报告 95% 区间。**文中当前生产设定 K=1，只评估 orchestrator，不能写成已分别估计所有子代理、工具和系统提示的贡献。**

来源：[Agent Arena 方法与公式](https://arena.ai/blog/agent-arena-methodology)

以下是由估计目标推导的阅读原则，不是对生产系统的新事实断言：

1. 相对参照池改变时，同一个模型的相对改进值可以改变。跨日期比较应保存 Q、候选模型集合与时间权重。
2. 随机分配有助于平台内的处理比较，但不会自动保证平台用户、任务、工具与别处部署一致。内部可识别性与外部适用性是两个问题。
3. 反馈是否出现可能受模型行为影响。只在有情绪反馈的任务上计算比例，需要单独报告反馈覆盖率，不能悄悄解释成所有任务的满意率。
4. 更少 bash 错误也可能来自更少尝试。可靠性、任务完成、调用量、费用和延迟应共同阅读，而不是任意一个信号独立代表总价值。
5. 低基准发生率的工具幻觉要连同样本量和区间报告。没有观察到事件不等于真实发生概率为零。
