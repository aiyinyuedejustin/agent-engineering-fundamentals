# Architecture decisions

**Status: scaffold only. No implementation architecture has been selected.**

Use architecture decision records (ADRs) to connect evaluation-infrastructure choices to research evidence. Keep proposed choices separate from accepted decisions and implemented behavior.

Each ADR should include:

- Decision ID, title, date, status, and scope.
- The concrete problem, constraints, and stakeholders.
- Considered alternatives and their supported trade-offs.
- Relevant source/evidence IDs and explicit assumptions.
- Decision, rationale, consequences, and remaining risks.
- What new evidence would trigger reconsideration.
- Implementation/reproduction artifacts, if any.

Statuses: proposed, accepted, superseded, rejected, or deferred. A proposed design is not an implemented or experimentally validated system. Do not mark an ADR accepted on behalf of the user without an applicable instruction.

For actual experiments, preserve the research question, commands/configuration, code revision, environment, model/data versions, seeds/budgets, run timestamps/status, raw outputs, and limitations in the owning research section. Link those artifacts here when they support a decision. A planned command is not D4 evidence.
