# 控制块P的写入与传递证据

固定输入：Linux amd64 native模块，SHA-256 `c3934f38ec5de0a2b6ef31641c28d8bec2fb125ff6a3a39b6dba84d9885cbca6`，大小10,026,272字节。所有地址均为该ELF虚拟地址；FDE表示从`.eh_frame`取得的函数覆盖范围。这里用P/T/D/F/C作为分析记号，不宣称恢复出了源码类型。

- P：0x18字节共享控制块
- T：文件异步任务，root为0x58字节，beneath为0x68字节
- C：`P+0x10`的字节
- D/F：任务结果判别器与execute确已写入的成功fd；初始化的`D=-1, fd=0`不等于F存在

## FCW-01：从分配点跟踪同一P，而不是按偏移猜对象

| 阶段 | openRootDir | openBeneath |
|---|---|---|
| P分配 | `0x62ef85/0x62ef8a`，大小0x18 | `0x61cb40/0x61cb45`，大小0x18 |
| P+8写1 | `0x62ef99` | `0x61cb54` |
| C写0 | `0x62efa1` | `0x61cb5c` |
| P保存到本地 | `0x62efa5`，栈+0x10 | `0x61cb60`，栈+0x28 |
| P首字段写2 | `0x62efb2` | `0x61cb96` |
| P保存到待复制任务槽 | `0x62efec`，栈+0x58 | `0x61cbc2`，栈+0x80 |
| 连同deferred复制到T | `0x62f012/0x62f017`，T+0x40 | `0x61cbed/0x61cbf5`，T+0x50 |
| create_async_work的数据参数 | `0x62f162`，r9=T；调用`0x62f165` | `0x61cdaa`，r9=T；调用`0x61cdad` |

P首字段的2是64位计数字段，不是C字节的2。它与C相隔0x10字节，不能混为“取消标志写2”。

GOT `0x98d7e8` 明确重定位为 `napi_create_async_work`。root在该调用指定execute=`0x619f10`、complete=`0x61b4d0`；beneath分别指定`0x619e80`、`0x61b230`。P通过T跨越这个已识别的FFI数据边界，而不是被直接注册为回调函数或JS值。

## FCW-02：queue成功后的本地句柄去向

### root

1. `0x62f1b0`调用`napi_queue_async_work`；`0x62f1b6/0x62f1b8`在返回0时进入`0x62f24d`。
2. `0x62f251`取Promise值；`0x62f261`重新取本地P。中途文字缓冲区的free不接受P。
3. `0x62f284..0x62f29b`构造一个本地五字段记录，含P、work、Promise、deferred、env。这个记录不能因“曾同时存在这些字段”就被称为已公开的取消对象。
4. `0x62f2a0`递减P首字段；为0才由`0x62f2b5`调用计数释放helper。该路线没有写C=2，也没有调用已识别的取消API。
5. Promise先保存在rbp（`0x62f28e`），再经`0x62ef19`或保留rbp的对应清理分支送到rax；成功标志r12=-1选择普通返回`0x62ed8f..0x62eda0`。

### beneath

1. `0x61ce01`调用queue；`0x61ce07/0x61ce09`在返回0时进入`0x61ce79`。
2. `0x61ce7d`取Promise到r13；`0x61ce8d`取P到rbp。
3. `0x61ceb8..0x61cecc`形成类似的本地记录；`0x61ced1/0x61ced5`仅向输出结构写Promise及成功判别器。
4. `0x61cedc`递减P首字段；必要时`0x61ceee`调用释放helper。
5. 外层callback `0x62d560..0x62d806`在`0x62d7d3`调用工厂，检查成功判别器后，`0x62d7e3`把输出结构+8的Promise送rax返回。

这些是**本地程序次序和数据去向**，不是实测线程调度，也不意味着queue返回前后worker/complete的全局时序已证明。没有以Promise对象不能被宿主或别处扩展为前提。

## FCW-03：execute没有沿这条P边检查取消

root完整execute FDE `0x619f10..0x619f96`：

- T保存在rbx
- 文件worker参数是栈上结果地址、T+8的路径指针、T+0x10的长度
- `0x619f25`调用worker `0x4f4670`
- `0x619f54/0x619f58`把worker结果写T+0x18/+0x20
- 其余结果写入最多覆盖T+0x3f；P在T+0x40，不与这些写入重叠

beneath完整execute FDE `0x619e80..0x619f10`：

- T保存在rbx
- worker参数是栈上结果地址、T+0x18的dirfd、T+8/+0x10的分量集合、T+0x1c/+0x20的flags/mode
- `0x619ea0`调用worker `0x4f3bc0`
- `0x619ecf/0x619ed3`写T+0x28/+0x30；其余结果写入最多覆盖T+0x4f，P在T+0x50

这两份execute的正常工作路径未直接读取P槽、不把T或P直接传给文件worker，也不根据C分支。异常落点则不同：beneath的`0x619efc → 0x619eff → 0x6179f0`、root的`0x619f82 → 0x619f85 → 0x617860`会把T交给cleanup；这些helper读取P并做引用清理。因此不能声称整个execute连同callee的所有效果都不访问P。这里也没有追查宿主如何决定是否调用execute；不能把“正常工作路径没有C检查”扩大成“外部永远不能取消任务”。

## FCW-04：同一P在complete中的读与写

| 动作 | root | beneath |
|---|---|---|
| 取T中的P | `0x61b52a`，T+0x40 | `0x61b28c`，T+0x50 |
| 读C | `0x61b52e` | `0x61b290` |
| 比较C=2 | `0x61b532` | `0x61b295` |
| C=2路线调用delete work | `0x61b539` | `0x61b29b` |
| 该路线重新取P并写C=1 | `0x61b53f/0x61b543` | `0x61b2a1/0x61b2a5` |
| 正常交付/报错后的共同清理写C=1 | `0x61b64f/0x61b653` | `0x61b3a0/0x61b3a4` |

status=11会更早进入抑制结算路线，不需要C=2。两者是不同的输入条件，不能合并成同一个取消事件。

共同计数helper `0x709270..0x709286`先从传入的指针槽取P，减P+8计数，必要时跳到free。没有字节访问或C写入；它不是隐藏的写2函数。异常cleanup `0x617860`/`0x6179f0`同样以计数递减及该helper清理P，不把本地引用释放变成取消请求。

## FCW-05：找到写2指令，仍不等于找到这个P的写入者

候选FDE `0x778620..0x778638`对输入低字节sil做映射，并在`0x778634`原子交换`[rdi+0x10]`：

| sil | 写入字节 |
|---|---|
| 0 | 0 |
| 2 | 2 |
| 其他非0值 | 1 |

它有7个`R_X86_64_RELATIVE`表槽引用：`0x984f78`、`0x985660`、`0x9860f8`、`0x986ff8`、`0x988b50`、`0x98a218`、`0x98aa98`。**没有恢复出“文件任务P被送入这些表的对应间接调用，且sil=2”这条边。** 因此保留为未关联候选，不能把rdi强行命名为文件控制块。

另一些看似相同的直接写入足以说明纯搜索的风险：

- `0x5a8a42`写的是刚分配0x24字节对象的一部分初始化，与这里0x18字节的P分配链不同
- `0x77934a`在解析包含连字符/`urn:uuid:`形式的输入后写一个结果结构；它的地址/长度载荷不能解释成这里的两个计数字段
- `0x612815`处的局部状态机还把同一基址的首字段当指针解引用，不能仅按`+0x10`相同就认定为P

`candidate-inventory.json`记录39个直接常量写2及9个相同偏移原子操作的语法位置。它不涵盖调整基址后的写入、普通寄存器值写入、宽写入或间接函数效果，也没有完成所有候选的可达性证明。

动态重定位表没有名为`napi_cancel_async_work`的导入。这只能说明该表没有该名字；模块仍有`dlopen`/`dlsym`导入，宿主行为也在范围外，所以它不证明取消API或等价效果绝不存在。

## 证据边界与下一项真正需要闭合的边

已有的窄链是：P分配 → C=0 → P进入T → queue成功后本地计数递减/Promise返回 → execute未按C决定是否调用文件worker → complete读C并最终写1。

仍缺的是：**某个可由真实调用入口到达的主体，如何取得同一P及相关work，如何把C变成2，和它相对execute/complete的顺序。** 目前不能把未关联的表驱动写入者接到这条链，更不能由“没有搜到连接”得出“C=2不可达”。

本轮不改变上一轮关于已有F时抑制交付的条件推演，也不把未发生execute时的初始fd=0当作已打开描述符。只有先闭合写入者与时序，才适合继续讨论`F存在 ∧ C=2`的运行时所有权。
