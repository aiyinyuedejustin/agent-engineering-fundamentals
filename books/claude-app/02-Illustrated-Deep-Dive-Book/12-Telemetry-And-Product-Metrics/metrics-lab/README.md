# 原创 AI 任务指标实验

这个标准库 Python 实验演示事件契约、运输去重、任务与尝试分母、成熟窗口、终态时间矛盾隔离、未知终态、顺序漏斗和条件延迟分位数。它是原创教学代码，不是 Claude 的实现。

## 运行

```bash
python -m unittest -v test_metrics_lab.py
python metrics_lab.py sample-events.jsonl 2000000
python metrics_lab.py adversarial-events.jsonl 2000 1000
```

第二个参数是固定分析截止时点，第三个可选参数是观察窗口长度；默认窗口为 600,000 毫秒。相同输入快照、截止时点和窗口才会得到相同结果。所有输入都是合成数据，运行不需要网络或第三方 Python 依赖，也不会向任何系统发送遥测。

## 精确契约：先确定能说什么

### 1. 标识、校验与到达顺序

- 任务键是 `(user_id, task_id)`；尝试键再加 `attempt_id`。不同用户的同名任务互不污染。运输去重键是 `(user_id, event_id)`，因此同一用户不能把一个 event ID 用于两个任务。
- 此 schema 没有组织字段。`user_id` 必须是当前数据集内无冲突的用途受限身份；跨组织汇总时，上游必须提供无冲突的身份命名空间。不能仅凭组织内局部 ID 合并，也不能声称本实验已经解决账户切换或身份合并。未知的 `organization_id` 字段会被拒绝。
- 时间必须是非负整数毫秒；布尔值、浮点数、NaN 和无穷值均不接受。Python 整数没有本实验另设的最大时钟值，跨语言系统应另外约定可表示范围。窗口必须为正整数。
- 先校验所有事件和运输 ID 冲突，再排除 `time_ms > as_of_ms` 的未来事件。即使非法记录最终会被时间或同意筛选排除，也不会跳过 schema 校验；非法字段或冲突 event ID 使整批失败，不输出可信的部分指标。
- 同一运输 ID 的相同内容只算一次。乱序输入按业务事件时间解释，不按行顺序、event ID 或到达先后猜测状态。相同毫秒允许并列，不虚构更细的先后关系。

### 2. 同意、锚点与观察窗口

在截止时点内，同一任务只要出现 `consent=false`，整个任务退出指标队列；真假混合单独计入 `mixed_consent_tasks`，全假计入 `nonconsenting_tasks`。不能先删掉未同意事件，再把剩余半条任务当作完整日志。该保守规则也适用于指标窗口之外但截止时点以内的记录；未来记录不提前影响当前快照。

这只是合成离线日志的排除策略，不是撤回同意、保留、删除或真实授权状态系统。生产采集端仍必须独立执行同意与删除策略；本程序不应被用来证明曾经收集未同意数据是合理的。

候选任务必须有且仅有一个去重后的 `task_submitted`，预先声明合格，并且 `提交时间 + horizon_ms <= as_of_ms`。提前成功或失败也不能缩短成熟窗口。无提交事件是孤立任务；不同 event ID 的重复提交即使时间相同也没有唯一锚点，保持原有隔离语义，不凭空选择第一次。

指标窗口为闭区间 `[提交时间, 提交时间 + horizon_ms]`。成熟合格任务出现提交之前的事件时隔离。窗口之后的记录计入 `events_after_horizon`，不改写该窗口的执行指标；因此这里检查的是固定窗口的契约，不是整个任务生命周期的证明。

### 3. 权威终态与尝试边界

`task_closed` 是本模型的不可逆执行终态。窗口内只能存在一个 `(业务时间, outcome)` 组合。重复发射若保持该组合不变，可按逻辑重复计数；相同 outcome 却改了关闭时间，也进入 `conflicting_task_closes`，不能默默取较早时间来美化延迟。

窗口内的 `attempt_started`、`attempt_finished`、`first_output_visible` 必须不晚于任务关闭时间；任何一个出现在关闭之后，都将整个任务隔离为 `activity_after_task_close`，不贡献成功数、延迟或重试数。同毫秒允许。需要关闭后重新执行的产品，应使用新的任务 ID，或另行设计显式重开契约，不能直接套用本模型。

同一尝试的开始时间和 `(结束时间, outcome)` 也必须分别唯一；保持业务时间的逻辑重复可去重，改变边界则隔离。若开始事件存在，结束或可见输出不能早于它。执行结束后 UI 才展示输出是允许的，只要没有晚于任务关闭；本程序不把执行完成与屏幕可见混为一谈。

缺失不是矛盾。缺少 attempt 开始或结束不自动删除一个有可信 task 终态的任务，也不推导失败、补造尝试或强行补齐漏斗。`attempt_coverage` 只对最终保留队列报告缺少哪些尝试边界，以及没有任何尝试证据的任务数。它不能发现完全缺失、从未出现任何记录的尝试。

`retry_task_count` 保留字段名，但准确口径是：最终保留的成熟任务中，窗口内至少有两个不同 attempt ID 的启动。它不再包含已知的关闭后启动；仍不能证明这些启动一定是顺序重试，而不是并行分支或缺失事件后的不完整记录。

### 4. 价值信号不是权威终态

仅成功关闭时刻或之后、且窗口内的 `value_confirmed` 才贡献价值计数。没有关闭、关闭为失败/取消，或信号早于成功关闭时，保持原有“不计价值”的口径，并新增 `uncredited_value_confirmations` 诊断。此类信号不会合成成功终态，也不会单独使任务被隔离。重复可见阶段取最早可见时间；重复价值信号不重复计任务。

## 分母不能随着隔离悄悄消失

`denominator` 和边际比率仍描述最终通过质量筛选的任务。同时必须展示：

- `cohort_accounting`：截止时点内观察到的任务键、同意排除、孤立、提交歧义、不合格、未成熟、质量筛选前候选、最终保留和候选内隔离数。
- `quarantine_reasons`：每种理由影响多少任务。一个任务可以有多个理由，但只被隔离一次；这里不能把理由计数求和当任务总数。
- `success_fraction_sensitivity`：设候选数为 C，最终保留队列中已确认成功为 S，未知终态为 U，候选内隔离为 Q；保守敏感性范围为 `[S/C, (S+U+Q)/C]`，C=0 时两端均为 null。

这个范围假设保留的权威终态可信，把未知与隔离任务的成功状态都视为未确定。它不是置信区间、因果效果或偏差修正，也不覆盖被同意策略排除的任务、没有提交记录的任务、提交锚点歧义任务或根本没有送达日志的任务。按实验组比较时，还需分别检查这些排除和缺失是否不平衡。

`observed_task_keys` 等于同意排除、孤立、提交歧义、不合格、未成熟和候选这六个互斥桶之和；候选数等于最终保留数加候选内隔离数。`quality.quarantined_tasks` 还包括提交歧义，因此不一定等于候选内隔离数。

## 手算样例

[原始样例](sample-events.jsonl)有三个成熟任务：一个成功且确认价值、一个失败、一个未知。另有一个尚未完成观察窗口的任务。一条运输重复记录被去重，一个失败任务观察到两次尝试启动。

- 分母：3；首输出任务：2；成功任务和价值确认任务各 1
- 成功率与价值确认率：都是 1/3
- 已观察首输出时延：100 ms 和 400 ms；最近秩定义的 P95 为 400 ms
- 多启动任务：1；未成熟任务：1；运输重复：1
- 候选仍是 3，隔离为 0；未知终态使成功比例敏感性范围为 `[1/3, 2/3]`
- 观察到 3 个 attempt ID，但 2 个没有结束记录；另有 1 个任务没有尝试记录。这些缺失原本就在样例中，新增覆盖诊断使它们可见

这些原有指标值保持不变。[更新后的固定输出](sample-result.json)新增队列、覆盖和敏感性诊断，所以文件本身和哈希会变化。

[对抗样例](adversarial-events.jsonl)有 11 个观察到的任务键：2 个同意排除、1 个孤立、1 个提交歧义、1 个不合格、1 个未成熟和 5 个候选。5 个候选中，关闭后启动与关闭时间改变各隔离 1 个，留下 3 个；其中 2 个成功、1 个未知。筛选后成功率是 2/3，但候选隔离率为 2/5，敏感性范围是 `[2/5, 1]`，不能只发布那个 2/3。[对抗固定输出](adversarial-result.json)可通过上面的第三条命令逐字节复现。

74 个单元测试包括原有 26 个测试和 48 个新增测试方法；还覆盖 120 种小日志排列、25 次固定种子重排、时间边界、并列时间、重复终态、缺失阶段、混合同意、用户命名空间和两个命令行快照。

## 明确限制

- 输入必须能放入内存，没有流式 watermark、到达时间、持久化 checkpoint 或跨批次状态。后来到达的旧事件可以改变同一截止时点的结果；截止时点本身不保证数据完整。
- 只支持未采样数据；不外推到未同意遥测的用户。不把 unknown 当作已观察到的 failure。
- 首输出与成功完成的分位数是条件分布；必须同时报告无输出、未知、未成熟、隔离和排除规模。
- 不是完整 attempt 状态机，不要求每个起止事件齐全，不验证所有并行与重开规则，不计算因果效果、置信区间或生产级异常上报。
- 字段白名单不会识别标识符内的个人信息；真实系统必须单独生成用途受限 ID，并管理权限、保留和删除。
